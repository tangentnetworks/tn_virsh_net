# TN_VIRSH_NET_SET.sh

**Tangent Networks** -- virsh network definition generator and subnet analysis
tool for GNU/Linux.

A POSIX `sh` script that takes an IPv4 CIDR subnet, derives a matching ULA
IPv6 `/64`, prints a full subnet analysis, and optionally writes a
`virsh net-define`-ready XML network definition.  Three topology profiles are
supported: NAT gateway, routed segment with a VM acting as egress router, and
isolated (air-gapped) segment.  The script is equally useful at the Linux
console with no virsh involvement at all.

---

## Features

- Pure POSIX `sh` -- no bash, no external math tools; works under `dash`
- Dual-stack from the start: every definition carries both IPv4 and IPv6
- Deterministic ULA IPv6 derivation from the IPv4 subnet (TN scheme,
  documented below)
- Three topology profiles with tailored XML recipes and post-activation hints:
  - **NAT** -- libvirt dnsmasq gateway; VMs share host internet
  - **Route** -- VM as egress router; libvirt creates bridge only
  - **Isolated** -- air-gapped segment; DHCP by libvirt, a VM, or none
- DHCP start at host offset +10 for both IPv4 and IPv6 (convention matches
  across the TN fleet)
- Bridge names automatically truncated to the 15-character Linux `IFNAMSIZ`
  limit
- Overwrite guard on existing XML files
- Coloured terminal output; degrades cleanly to plain text when stdout is not
  a tty

## Usage

```sh
sh TN_VIRSH_NET_SET.sh
```

The script is fully interactive.  It walks through up to eight stages
depending on the answers given:

```
Stage 1   Mode selection         -- console subnet analysis, or also write virsh XML
Stage 2   IPv4 subnet input      -- CIDR notation, validated
Stage 3   IPv6 derivation        -- ULA /64 derived automatically; results displayed
Stage 4   Topology profiling     -- NAT | Route | Isolated  (virsh path only)
Stage 4a  Topology sub-questions -- services, interface names, host DHCPv6
Stage 5   virsh network name     -- used in <name> and output filename
Stage 6   Output directory       -- created if absent (with confirmation)
Stage 7   XML generation         -- topology-specific recipe written to disk
Stage 8   Summary and hints      -- activation commands printed
```

Stages 4 through 8 are skipped entirely when console-only mode is chosen at
Stage 1.

## Topology profiles

### 1 -- NAT

libvirt acts as the default gateway for VMs on this segment.  dnsmasq
provides DHCPv4 and DHCPv6.  Outbound traffic is NATed through the host.
Standard choice for development or general-purpose VM networks.

**What libvirt does:** creates the bridge, assigns the gateway address to it,
starts dnsmasq, adds iptables NAT rules.

**Example session:**

```
  Generate a virsh XML network definition? [y/N]: y
  Enter IPv4 Subnet: 10.0.0.0/24
  Topology [1/2/3]: 1
  Enter virsh network name: tn-lan0
  Enter output directory: /etc/libvirt/networks
```

**Generated XML (`net_tn-lan0.xml`):**

```xml
<network>
  <!-- Generated by TN_VIRSH_NET_SET.sh v2.0.0 -->
  <!-- Topology : NAT -- libvirt dnsmasq gateway -->
  <!-- IPv4     : 10.0.0.0/24   IPv6: fd0a:0000::/64 -->
  <name>tn-lan0</name>
  <forward mode='nat'>
    <nat>
      <port start='1024' end='65535'/>
    </nat>
  </forward>
  <bridge name='virbr-tn-lan0' stp='on' delay='0'/>

  <!-- IPv4: host bridge = 10.0.0.1  DHCP 10.0.0.10-10.0.0.254 -->
  <ip address='10.0.0.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='10.0.0.10' end='10.0.0.254'/>
    </dhcp>
  </ip>

  <!-- IPv6: host bridge = fd0a:0000::1/64  DHCP fd0a:0000::a-fd0a:0000::fe -->
  <ip family='ipv6' address='fd0a:0000::1' prefix='64'>
    <dhcp>
      <range start='fd0a:0000::a' end='fd0a:0000::fe'/>
    </dhcp>
  </ip>

</network>
```

**Activate:**

```sh
virsh net-define    net_tn-lan0.xml
virsh net-start     tn-lan0
virsh net-autostart tn-lan0
```

### 2 -- Route (VM as egress router)

A VM on this segment acts as the egress router.  libvirt creates the bridge
and installs a host route; it does **not** start dnsmasq and does **not**
assign an address to the bridge interface.  The VM owns DHCPv4, DHCPv6, and
IPv6 RA on the segment.

The script asks for:

- VM segment-side interface name (for documentation in XML comments and hints)
- VM WAN/egress interface name (for documentation)
- Whether the VM will run DHCPv4, DHCPv6, and/or RA
- Whether the host bridge should acquire its IPv6 via DHCPv6 client from the VM

**Typical addressing:**

```
VM segment-side interface  10.0.1.1 / fd0a:0001::1   (static, configured in VM)
Host bridge                          fd0a:0001::a      (from VM's DHCPv6 client)
VM clients                10.0.1.10-10.0.1.254        (from VM's dnsmasq)
```

**Example session:**

```
  Generate a virsh XML network definition? [y/N]: y
  Enter IPv4 Subnet: 10.0.1.0/24
  Topology [1/2/3]: 2

  VM segment-side interface (e.g., eth0, enp1s0) [Enter to skip]: eth0
  VM WAN/egress interface   (e.g., eth1, enp2s0) [Enter to skip]: eth1

  VM will run DHCPv4?              [Y/n]: y
  VM will run DHCPv6?              [Y/n]: y
  VM will run IPv6 RA (radvd/radv)? [Y/n]: y
  Host bridge acquires IPv6 via DHCPv6 from the VM? [y/N]: y

  Enter virsh network name: tn-router0
  Enter output directory: /etc/libvirt/networks
```

**Generated XML (`net_tn-router0.xml`):**

```xml
<network>
  <!-- Generated by TN_VIRSH_NET_SET.sh v2.0.0 -->
  <!-- Topology : Route -- VM egress router; libvirt bridge only, no dnsmasq -->
  <!-- IPv4     : 10.0.1.0/24   IPv6: fd0a:0001::/64 -->
  <!--
    VM segment-side IF : eth0
      assign static    : 10.0.1.1/24  (IPv4)
                         fd0a:0001::1/64          (IPv6)
    VM WAN/egress IF   : eth1
  -->
  <name>tn-router0</name>
  <forward mode='route'/>
  <bridge name='virbr-tn-router' stp='on' delay='0'/>

  <!--
    No <ip> elements: VM owns all addressing on this segment.
    Host bridge (virbr-tn-router) has no libvirt-assigned address.
    See activation hints for host-side configuration.
  -->

</network>
```

**Activate and configure:**

```sh
virsh net-define    net_tn-router0.xml
virsh net-start     tn-router0
virsh net-autostart tn-router0

# Inside the VM -- segment-side interface (eth0):
ip addr add 10.0.1.1/24       dev eth0
ip addr add fd0a:0001::1/64   dev eth0
ip link set eth0 up

# Inside the VM -- DHCPv4 (dnsmasq example):
dnsmasq --interface=eth0 \
        --dhcp-range=10.0.1.10,10.0.1.254,12h

# Inside the VM -- DHCPv6 + RA (dnsmasq example):
dnsmasq --interface=eth0 \
        --dhcp-range=fd0a:0001::a,fd0a:0001::fe,ra-stateless

# Host bridge -- acquire IPv6 from VM:
dhclient -6 virbr-tn-router
# or NetworkManager:
#   nmcli con modify virbr-tn-router ipv6.method auto
# or systemd-networkd:
#   /etc/systemd/network/virbr-tn-router.network  [DHCP] IPv6=yes
```

### 3 -- Isolated

Air-gapped segment with no external routing of any kind.  No `<forward>`
element is emitted.  Three DHCP sub-profiles are available:

| Sub-profile | Who runs DHCP | Notes |
|-------------|---------------|-------|
| `libvirt` | libvirt dnsmasq | host bridge gets the gateway address; full dual-stack DHCP |
| `vm` | a VM on the segment | no `<ip>` elements; VM owns addressing |
| `none` | nobody | `<ip>` elements without `<dhcp>`; static addressing only |

**Example -- isolated, libvirt DHCP (`net_tn-dmz.xml`):**

```xml
<network>
  <!-- Generated by TN_VIRSH_NET_SET.sh v2.0.0 -->
  <!-- Topology : Isolated -- air-gapped; libvirt dnsmasq manages DHCP -->
  <!-- IPv4     : 10.0.2.0/24   IPv6: fd0a:0002::/64 -->
  <name>tn-dmz</name>
  <!-- No <forward>: isolated segment, no external routing -->
  <bridge name='virbr-tn-dmz' stp='on' delay='0'/>

  <ip address='10.0.2.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='10.0.2.10' end='10.0.2.254'/>
    </dhcp>
  </ip>

  <ip family='ipv6' address='fd0a:0002::1' prefix='64'>
    <dhcp>
      <range start='fd0a:0002::a' end='fd0a:0002::fe'/>
    </dhcp>
  </ip>

</network>
```

**Example -- isolated, static only (`net_tn-static.xml`):**

```xml
<network>
  <!-- Topology : Isolated -- air-gapped; static addressing, no DHCP -->
  <name>tn-static</name>
  <bridge name='virbr-tn-static' stp='on' delay='0'/>

  <ip address='10.0.4.1' netmask='255.255.255.0'/>
  <ip family='ipv6' address='fd0a:0004::1' prefix='64'/>

</network>
```

## ULA IPv6 derivation scheme

The ULA `/64` is derived deterministically from the IPv4 subnet's first three
octets.  No random Global ID is generated; predictability is the explicit
design goal within a managed TN fleet.

```
Scheme:  fd[hex(O1)]:[hex(O2)][hex(O3)]::/64

10.0.0.0/24    ->  fd0a:0000::/64
10.0.1.0/24    ->  fd0a:0001::/64
10.0.5.0/24    ->  fd0a:0005::/64
10.10.10.0/24  ->  fd0a:0a0a::/64
192.168.1.0/24 ->  fdc0:a801::/64
192.168.4.0/22 ->  fdc0:a804::/64
```

The prefix `fd` places these addresses in the IANA-registered ULA range
`fd00::/8` with the L-bit set (locally assigned), consistent with RFC 4193.
The Global ID encodes `O1` in the high byte and `O2:O3` in the low bytes of
the 40-bit field.

**Non-overlap guarantee:** any two distinct IPv4 `/24` subnets within the same
`O1` space (e.g. the entire `10.x.y.0/24` range) produce distinct ULA `/64`s
because their `(O2, O3)` pairs differ.  The one caveat is that prefix length
is not encoded: `10.0.5.0/24` and `10.0.5.0/25` both map to `fd0a:0005::/64`.
Mixing prefix lengths for the same `(O1, O2, O3)` combination requires manual
verification.

## DHCP address convention

| Protocol | First DHCP address | Last DHCP address |
|----------|--------------------|-------------------|
| IPv4 | `network + 10` (e.g. `10.0.0.10`) | `broadcast - 1` (e.g. `10.0.0.254`) |
| IPv6 | `::a` (offset 10) | `::fe` (offset 254) |

Host offset +10 leaves `.1` through `.9` as a static reservation band
consistent across the TN fleet.  `.1` is conventionally the gateway.

## Bridge naming

Linux interface names are capped at 15 characters (`IFNAMSIZ - 1`).  The
script uses the prefix `virbr-` (6 characters) and takes up to the first 9
characters of the virsh network name:

```
virsh name: tn-lan0       ->  bridge: virbr-tn-lan0    (15 chars)
virsh name: tn-router0    ->  bridge: virbr-tn-router   (15 chars, truncated)
virsh name: tn-dmz        ->  bridge: virbr-tn-dmz      (14 chars)
```

## Output files

The script writes one file per run:

```
<output-directory>/net_<virsh-name>.xml
```

The file is ready for `virsh net-define` without modification.  The script
asks for confirmation before overwriting an existing file.
